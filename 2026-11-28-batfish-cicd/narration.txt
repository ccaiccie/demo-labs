Today we walk through a local Batfish network CI/CD lab that validates Cisco IOS-style router configurations before any change merges into main.

Batfish is an open-source offline network configuration analysis engine. Instead of spinning up virtual routers or testing changes on live hardware, Batfish reeds the router configuration snapshot, builds a mathematical model of OSPF, BGP, routing tables, and access control lists, and answers automated pytest queries through pybatfish.

Let's look at the lab container first. In docker-compose.yml, we run the official batfish/allinone:latest image, version 2026.08.27.3685, as batfish-lab. We bind only two ports to loopback: 127.0.0.1 port 9996 for the v2 REST API and 127.0.0.1 port 9997 for the coordinator service. Jupyter port 8888 is not published. The Docker healthcheck probes http://127.0.0.1:9996/v2/version until it returns HTTP 200 and the container reports healthy.

Now let's look at the four-router topology under snapshots/lab/configs. Every address in this lab uses RFC 5737 documentation space or RFC 1918 transit links with private autonomous system numbers. On the left, branch-rtr sits in AS 65100 with Loopback0 at 198.51.100.1/32, the Branch LAN on GigabitEthernet0/0 at 192.0.2.1/24, and an eBGP link to core-rtr1 over 10.10.12.0/30. In the middle, core-rtr1 and core-rtr2 share AS 65200. They run OSPF process 1 area 0 across their 10.10.23.0/30 transit link and loopbacks 198.51.100.2/32 and 198.51.100.3/32, and they peer over iBGP using Loopback0 with next-hop-self. On the right, edge-rtr sits in AS 65300 with Loopback0 at 198.51.100.4/32, an eBGP link to core-rtr2 over 10.10.34.0/30, and the Server LAN on GigabitEthernet0/1 at 203.0.113.1/24. Inbound on edge-rtr GigabitEthernet0/0, an extended access list named EDGE_IN permits BGP on TCP 179, permits HTTPS on TCP 443 and ICMP from 192.0.2.0/24 to 203.0.113.0/24, explicitly denies Telnet on TCP 23, and ends with an explicit deny any any rule.

To automate pre-merge validation, the repository includes a GitHub Actions workflow in .github/workflows/batfish.yml and a matching local runner script in ci/run_pipeline.sh. The script verifies that Batfish is reachable on 127.0.0.1 ports 9996 and 9997, confirms HTTP 200 on /v2/version, and runs five pytest checks in tests/test_network.py:
1. fileParseStatus and initIssues confirm every config file parses cleanly with zero warnings.
2. undefinedReferences confirms there are no dangling access lists or unreferenced objects.
3. bgpSessionCompatibility and bgpSessionStatus confirm all six directional BGP session rows are UNIQUE_MATCH and ESTABLISHED.
4. testFilters and searchFilters verify EDGE_IN on edge-rtr permits HTTPS TCP 443 and denies Telnet TCP 23 across the entire 192.0.2.0/24 to 203.0.113.0/24 space.
5. traceroute and reachability verify traffic from branch-rtr GigabitEthernet0/0 reaches the server subnet on TCP 443 without hitting NO_ROUTE, DENIED_IN, or NULL_ROUTED.

First, we run bash ci/run_pipeline.sh on the baseline main branch at commit 1a144e0. Batfish reeds the four configs and all five checks pass in 13.96 seconds with exit code 0.

Next, we test a good change on branch feat/allow-metrics-port at commit 9623f15. We add a single line to EDGE_IN on edge-rtr.cfg permitting TCP 8443 from 192.0.2.0/24 to 203.0.113.0/24 for metrics traffic. When we run ci/run_pipeline.sh, all five checks pass in 13.71 seconds with exit code 0, and we merge the branch into main at commit 1a7632a.

Now we test three bad changes on separate branches to see the pipeline catch each failure before merge.

Bad change one is on branch change/acl-block-https at commit d7a04c3. Here, an edit to edge-rtr.cfg flips the HTTPS TCP 443 rule in EDGE_IN from permit to deny. Running ci/run_pipeline.sh fails with exit code 1 in 20.38 seconds: three checks pass, and two fail. testFilters catches edge-rtr EDGE_IN returning DENY for 192.0.2.50 to 203.0.113.10 on port 443, and traceroute shows the packet traversing branch-rtr, core-rtr1, core-rtr2, and hitting disposition DENIED_IN at edge-rtr. On commit c0119ed, we restore the HTTPS permit line, re-run ci/run_pipeline.sh, and all five checks pass in 14.07 seconds. We merge the fix into main at commit 369f36e.

Bad change two is on branch change/bgp-peer-as-mismatch at commit 9d7717f. On core-rtr1.cfg, we change neighbor 10.10.12.1 remote-as from 65100 to 65199. Running ci/run_pipeline.sh fails with exit code 1 in 20.28 seconds: three checks pass, and two fail. bgpSessionCompatibility reports HALF_OPEN on both branch-rtr and core-rtr1 because the configured autonomous system numbers no longer match, and traceroute reports disposition NO_ROUTE right at branch-rtr since the server prefix is no longer learned. On commit 6423176, we restore remote-as 65100 on core-rtr1.cfg, re-run the pipeline, and all five checks pass in 13.05 seconds. We merge the fix into main at commit 499359d.

Bad change three is on branch change/missing-server-route at commit a236b3b. On edge-rtr.cfg, we remove the BGP network statement for 203.0.113.0 with mask 255.255.255.0. When we run ci/run_pipeline.sh, it fails with exit code 1 in 20.88 seconds: four checks pass, and one fails. Notice why end-to-end validation matters here: config parsing passes, undefined references pass, all six BGP sessions stay ESTABLISHED, and EDGE_IN still permits HTTPS, yet traceroute from branch-rtr GigabitEthernet0/0 to 203.0.113.10 port 443 fails immediately with disposition NO_ROUTE at branch-rtr. On commit fe6352f, we restore the 203.0.113.0/24 network advertisement on edge-rtr.cfg, re-run ci/run_pipeline.sh, and all five checks pass in 13.28 seconds. We merge the fix into main at commit b86d1ba.

Looking at git log --oneline --graph --decorate --all in evidence/git-log-graph.txt, the full branch history stays preserved as an audit trail: baseline main, the passing metrics feature branch, and all three broken-then-fixed change branches merged cleanly only after Batfish returns exit code 0.

Keep two practical limits in mind. First, Batfish performs static configuration modeling, so it catches routing, BGP, and ACL defects before deployment, but it does not replace monitoring for hardware faults or live runtime anomalies. Second, Batfish classifies traffic to subnet network and broadcast eye pee addresses ending in .0 and .255 as EXITS_NETWORK rather than DELIVERED_TO_SUBNET, which is why our positive reachability check targets the usable host eye pee range 203.0.113.1 through 203.0.113.254 while the failure check covers the full /24 prefix.
